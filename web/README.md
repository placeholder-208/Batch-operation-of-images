# 心裁

浏览器图片工作台：二维码识别与裁切、二维码遮盖、条形码识别、语义裁剪和本地分割。二维码、条形码和分割在本机运行；语义裁剪与可选的网页信息查询通过 Worker API 联网。

## 目录

```text
web/
├── index.html              页面入口
├── js/                     应用逻辑、图像处理及各功能界面
│   └── segmentation/       本地分割、提示与蒙版编辑
├── assets/                 品牌图片与当前样式
├── models/                 WeChat 检测、SlimSAM 与 MODNet FP32 模型
├── vendor/                 ORT WASM、分割运行库、PDF.js 及许可
├── zxing/                  ZXing 加载脚本和 reader WASM
├── server/                 Worker API 实现
├── worker.js               Cloudflare Worker 入口
├── wrangler.jsonc          部署配置
├── test/QRcode/            用户测试图片与四角标注
└── benchmarks/             本地评估、结果与历史归档
    ├── qr/                 QR 评估程序；archive/v3.9 保存旧更新材料
    ├── segmentation/       分割模型评估，独立于产品
    └── archive/            编辑器恢复文件与旧样式，不提交、不部署
```

## 工作台界面（3.17）

桌面端结果区独立滚动，导出区固定在检查器底部。点击结果卡片可定位，长内容可展开；统计与诊断位于折叠区。单张图片时缩略图栏收窄。

图片工具栏支持适合窗口、预览100%和200%；100%以预览画布像素显示，高倍查看不增加原图细节。切换“浏览”可拖动查看，放大后也可用滚动条或鼠标中键平移；编辑时切回“绘制”。只读码预览允许手指纵向滚页。

本地分割的蒙版修整工具靠近画布，保留/擦除使用分段按钮，右键切换会同步。当前结果为人物连续透明度时隐藏不适用的候选、阈值和窄边抗锯齿，反转仍可用。重新生成与批量设置收在折叠区。手机端主操作与导出入口固定在底部，画笔条位于预览下方。

二维码、条形码和遮盖支持停止本批：当前图片处理结束后停止，未开始的图片可继续处理。清空/移除需在3秒内再次点击确认；刷新恢复显示提示，本机保存状态附最近保存时间。

UI浏览器验证与运行方法见 [benchmarks/ui/README.md](benchmarks/ui/README.md)。

## QR 正式流程（v3.16）

v3.16为已解至少8码、WeChat候选明显偏少的密集多码图追加有预算的重叠块检测；原路径仍失败时，末尾补做有限相位采样。稀疏照片不触发此路径，旧整图结果和原候选优先保留。用户30码手持照片从27提升至30；95张默认/精细回归的逐图内容和坐标不变，详见 [密集多码修复](benchmarks/qr/experiments/dense-sheet/REPORT.md)。

每图一次基础 ZXing 解码 → WeChat 补充候选 → 对未覆盖候选依次进行原区域解码和四种局部增强 → 对剩余失败区域进行柱面校正 → 原模块二值采样仍失败时，补充连续灰度采样 → 对仍未解决的局部区域补做受限去模糊恢复。

去模糊采用有限组高斯/直线运动模糊假设的 Wiener 恢复，再交由 ZXing 验证。默认先在384像素工作边尝试17种滤波，失败后在448像素补试5种高斯核；“精细模糊恢复”默认关闭，开启后再以576像素补试17种滤波。尺寸不超过原区域大小，相同实际尺寸不重复处理，核宽随工作分辨率同比调整。每图最多3个区域；默认区域1500ms/整图4500ms，精细模式3500ms/10500ms，均在任务间检查，不是严格中断期限。只处理原流程仍未解决的区域，不修改原图与导出裁图像素；恢复坐标映射回原图并参与正常去重。

区域一旦被成功结果覆盖就停止继续加工该区域，继续处理其他候选。保留原区域与几何预算。TPS 与精细模糊恢复均默认关闭，可在“识别选项”中独立打开。TPS失败后仍尝试柱面校正。旧的调整顺序开关已退役，旧工作状态中的该设置会忽略；识别选项和图片、结果、历史统计继续恢复。

精细模式在上述分级恢复之后，先对最多3个未解决原区域补做结构灰度校准：以三个定位方块和时序线的黑白均值校准灰度，直接取模块中心，再试4个阈值，由普通ZXing验证。先384像素工作边，失败后448，不超过原区域且不重复实际尺寸；最多12模型/级、96次解码/区域。区域2500ms、整图7500ms，拟合600ms/级、采样1000ms/级，均为协作式预算。该步骤不搜索相位，也不往结果中填入已知图案或文本。

结构校准失败后，精细模式仍以完整原预算对最多3个候选补做“恢复后校正”，优先处理此前已有几何模型的区域，允许此前因预算跳过或未找到结构的区域在恢复图上重新寻找定位方块。固定使用不超过原区域的384像素工作边，对17种既有恢复核按7×7已知结构匹配度保留最多4张，再重新拟合柱面模型。该分数不是置信度；区域7000ms/整图14000ms、探测200ms/次、拟合600ms/图，均为协作式预算。

上述恢复图的原二值与连续灰度解码均失败后，补试模块灰度恢复：在拟合网格的灰度值上减少相邻模块串扰，再尝试有限阈值；最多12个不同几何模型、180次解码或1000ms。只以ZXing有效解码确认结果，不填写已知文本或功能图案。默认模式不运行这些追加步骤，不挤占原有恢复阶段的预算，也不改变原图和导出裁图。

全量95张测试中，默认仍为109/123；精细模式从v3.14的112/123增为114/123，新增blurred/image005.jpg两处目标，两次完整回归均保留全部旧成功内容哈希。曲面组仍60/60。数据集参与开发，需要独立图片验证；失败实验、裁剪留边敏感性与成本见 [v3.15报告](benchmarks/qr/experiments/finder-recovery/REPORT.md)，此前研究见 [v3.14报告](benchmarks/qr/experiments/structure-recovery/REPORT.md)。

统计 CSV 保留全部原列和人工补记字段，包括供历史轮次比较的“调整检测顺序”列；新轮次该列恒为“是”。JSON 记录 `pipeline: region-first`、版本、各阶段及采样方式。统计中的“全部识别”仅代表已发现的候选全部覆盖，未知漏检仍需人工补记。

v3.13在CSV末尾追加恢复后校正的尝试数、滤波数、准备、探测、拟合及解码耗时。JSON中的`restoredGeometry`记录筛选版本、探测和拟合结果；`restored_geometry_total`与`restored_geometry_fit`是父阶段，不能与其子阶段重复相加。

v3.14继续在CSV末尾追加模块恢复的解码次数、准备/解码耗时与预算跳过数，保留原列和人工字段。模块恢复解码耗时是恢复后ZXing总耗时的子集；其准备和解码也已包含在恢复后拟合父阶段中，不能重复相加。

v3.15继续在CSV末尾追加结构校准的区域数、次数、准备/拟合/采样/解码耗时及预算跳过数。JSON的`structureSampling.tiers`记录实际工作尺寸、几何诊断和所用黑白亮度；`structure_total`为父阶段，不能与子阶段重复计时。

## 本地分割模式

主页面「本地分割 → 处理 → 分割模式」可选「通用对象 · SlimSAM」或「人物精细抠图 · MODNet FP32」。默认仍为通用模式；人物模型约 26 MB，首次生成时才加载，图片只在浏览器后台线程中处理。模型文件位于 `models/segmentation/modnet/`，部署时需包含该目录，保持现有 Workers 静态资源部署方式，无需新增 API 或密钥。

人物模式仅使用白色裁剪范围，不使用蓝框或保留/排除提示点，可能同时保留多个人物。其输出是连续透明度，不应用 SAM 的蒙版阈值或窄边抗锯齿；仍可反转、用圆形/曲线画笔修整、清理小区域、批量导出 PNG/ZIP/CSV。模式选项用于后续生成，不自动覆盖已有结果；相同裁剪范围内重新生成会保留修整，失败则保留旧结果。批量任务使用当前模式、跳过已有结果，各图可保留不同模型的结果，CSV 追加模型与精度列。刷新恢复模式、结果和修改，兼容此前 SlimSAM 缓存。切换模型时释放另一模型会话以降低同时驻留内存。

人物模型不是动物或通用物品的精细抠图保证；发丝周围仍可能残留原背景颜色。工作图长边≤1024，透明 PNG 映射回原始裁剪尺寸，不代表原生大图精度。手机与低内存设备性能仍待验证。

接入测试和运行方法见 [主页面接入记录](benchmarks/segmentation/portrait/INTEGRATION.md)，选型实验见 [人物边缘报告](benchmarks/segmentation/portrait/REPORT.md)。

## 本地检查与部署

从本目录运行 Wrangler 开发服务器可同时测试静态页面与 Worker API。普通 `python -m http.server` 仅用于静态预览，不能处理 `/api/*` 请求。部署配置继续使用本目录作为 Cloudflare 静态资源根目录。

`.assetsignore` 排除测试数据、评估工具、开发配置与文档；不要删除模型、WASM、PDF.js 字库或供应商许可证。部署、推送和提交由开发者自行执行。

### 部署后首页异常

Cloudflare Git 集成的 Root directory 应为 `web`，部署命令为 `npx wrangler deploy --config wrangler.jsonc`，由该目录的配置同时部署 Worker 和静态资源。不要只上传 `worker.js`，也不要用普通文本变量代替 `assets.binding`。

上线后可直接打开 `/api/deployment-status` 自检。正常返回 `revision: assets-check-2026-10-24`、`assetsBinding: true`、`homepageStatus: 200` 和 `ok: true`。该接口仅读取静态首页，不调用外部 API，不读取或输出密钥、口令、图片或识别内容。`assets-binding-missing` 表示部署中没有可调用的 ASSETS 绑定；`assets-fetch-failed` 表示绑定调用异常；`assets-homepage-unavailable` 表示绑定返回了非 200 的首页响应，结合 `homepageStatus` 检查静态目录。自检正常仅证明当前 Worker 可读取首页，不代表已验证所有前端资源。

静态资源入口的绑定缺失或调用异常现在返回明确的 503 诊断代码，完整原因应查服务端日志。配置已启用 Workers Logs，重新部署后生效；Live 实时日志与保存的 Workers Logs 是不同功能。如果自检仍返回 Cloudflare 1101 HTML，而没有上述 JSON，异常可能发生在处理函数执行之前或平台内部，不能仅凭 1101 判断为绑定缺失。

部署入口检查：`node --experimental-default-type=module --test benchmarks/worker/deployment.test.mjs`。这是路由与异常处理的本地模拟检查，不代替 Cloudflare 线上验证。
